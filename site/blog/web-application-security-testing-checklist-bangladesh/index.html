Security Testing in Bangladesh: A Web Application Checklist

By Moinul Islam · 23 November 2026

Security testing in Bangladesh follows the same method as anywhere else: agree the scope, then test login and sessions, access control, input handling, payment logic and server configuration against the OWASP Top 10. This checklist is written for QA teams working on fintech, e-commerce and HRMS web applications who want a repeatable security pass before each release.

It uses free tools (Burp Suite Community, OWASP ZAP, browser DevTools and curl) and maps to the OWASP Web Security Testing Guide. It does not replace a full penetration test, but it catches the common, expensive mistakes early.

Only test applications you're authorized to test: your own product, a staging environment you have written permission for, or a bug bounty programme whose scope includes the target. Never run these checks against someone else's live site.

1. Set the scope and the test environment

Before the first request, write down what is in scope: domains, environments, user roles and the features you will touch. Test on staging with test data. For payment flows, use the gateway's sandbox, so no real money moves. Create at least two accounts per role, because most serious bugs need a second user to prove.

  • List every role (customer, merchant, admin, support) and what each should be allowed to do.
  • Keep a list of the endpoints you find while clicking through the app, from the Burp Suite or ZAP proxy history.
  • Agree who receives findings and how quickly they will be triaged.

2. Test login, OTP and sessions

Many Bangladeshi products sign users in with a phone number and a one-time password (OTP), so test that flow as carefully as a password login.

  • Brute force: after a set number of wrong passwords or OTP attempts, does the app lock the account or slow down? Can the OTP be guessed within its lifetime?
  • OTP handling: is the OTP single-use, short-lived and tied to one user? Does the response body leak it? Can "resend OTP" be called without limit, which costs the business money in SMS?
  • Error messages: do "user not found" and "wrong password" look different? That lets an attacker list valid accounts.
  • Session cookies: they should be HttpOnly, Secure and have a SameSite value. A new session ID should be issued after login.
  • Logout and reset: the old session must stop working after logout and after a password change.

If the app uses tokens, run the JWT testing checklist as well.

3. Test access control on every object

Broken access control is the top item in the OWASP Top 10, and it is the bug QA teams are best placed to find. Log in as user A, copy a request that returns A's order, invoice, payslip or wallet statement, then replay it with user B's session. If B can read or change A's data, you have an IDOR. Do the same across roles: can a customer open an admin URL by typing it?

The full method, with Burp Suite and Autorize, is in the IDOR testing checklist.

4. Test input handling: SQL injection and XSS

Every field that reaches the server or comes back on a page needs a quick check: search boxes, filters, profile names, comments, and URL and header values. Use harmless probes first:

# SQL injection signal: a stray quote should not produce a database error
GET /products?category=shoes'

# Reflected XSS signal: does the marker come back unescaped in the HTML?
GET /search?q=<b>probe123</b>

A database error, a changed result count or a marker rendered as real HTML is a finding. Confirm it, then stop. You don't need to dump data to prove the bug. The fixes are parameterized queries for SQL injection, and output encoding plus a Content Security Policy for XSS.

5. Test payment and business logic

Scanners miss logic flaws, so this section needs a person. It matters most for e-commerce checkouts, wallet top-ups and payroll or HRMS approvals, where a logic gap turns into lost money. Work in the gateway's sandbox and try these:

  • Price and quantity tampering: change the amount, use a negative quantity or switch the currency in the checkout request. The server must recompute the total itself.
  • Gateway callback: the payment success or IPN callback must be verified on the server. Can you mark an order as paid by calling the success URL yourself, or by replaying an old callback?
  • Double submission: send the same payment or coupon request twice at the same moment. Is it applied twice?
  • Coupons and balances: reuse a single-use coupon, stack discounts and try to withdraw more than the balance.
  • Workflow skipping: call the "confirm order" or "approve leave" endpoint without completing the earlier steps.

6. Check transport security, headers and exposed files

These checks take minutes and often find easy wins. Start with the response headers:

curl -sI https://staging.example.com | grep -iE "strict-transport|content-security|x-frame|x-content-type|server|x-powered-by"
  • HTTPS: HTTP redirects to HTTPS, and Strict-Transport-Security is set.
  • Security headers: Content-Security-Policy, X-Content-Type-Options and a framing policy (X-Frame-Options or frame-ancestors).
  • Information leaks: version banners in Server or X-Powered-By, stack traces on error pages, and debug mode left on.
  • Exposed files: /.git/, .env, backup files, database dumps and public admin panels.
  • CORS: a wildcard or reflected origin on an API that uses cookies is a red flag.

7. Check file uploads and the API layer

Profile pictures, document uploads and CSV imports are common in business apps. Check that the server validates the real file type and not just the extension, limits file size, and stores uploads where they cannot be executed. Then check the API behind the UI: every endpoint the mobile app uses needs the same authentication and access checks as the web pages, and responses should not return more fields than the screen shows.

8. Scan, then report and retest

Run an OWASP ZAP baseline scan against staging for the passive checks, and use the results as a to-do list, not a verdict. To run it on every pull request, see QA automation and security testing in one CI pipeline.

Write each finding so a developer can reproduce it in five minutes: a title that states the impact, the exact request, the response, the affected roles and a suggested fix. Rate severity by what an attacker could actually do, then retest after the fix and add an automated regression test. Key takeaways

  • Get written scope, and test on staging with test accounts and a payment sandbox.
  • OTP flows need the same abuse testing as passwords: guessing, reuse and unlimited resends.
  • Access control and payment logic cause the costliest bugs and need manual testing, not only scanners.
  • Check headers, error pages and exposed files, because they take minutes.
  • Turn each confirmed finding into an automated regression test. Reference: OWASP WSTG.

FAQ

Do I need to be a hacker to do security testing as a QA engineer?

No. A QA engineer already knows the roles, workflows and edge cases of the product, which is most of what access-control and logic testing needs. Learn a proxy such as Burp Suite or ZAP, work through the OWASP Top 10, and practise on legal labs like PortSwigger Web Security Academy before touching real projects.

What is the difference between security testing and penetration testing?

Security testing is the broader activity of checking that security requirements hold, and QA teams can do it on every release. A penetration test (or VAPT) is a time-boxed, deeper engagement that tries to exploit weaknesses, usually by a specialist team. They complement each other.

Which free tools should I start with?

Browser DevTools and curl for the basics, Burp Suite Community Edition or OWASP ZAP as an intercepting proxy, and Postman or Playwright to turn findings into automated checks.
