API Security Testing Checklist for QA Engineers

By Moinul Islam · 26 November 2026

To test API security as a QA engineer, send every endpoint the requests it should refuse: another user's object ID, an admin-only function called by a normal user, extra fields in the body, and hundreds of requests in a row. If the API answers any of them with 200, you have found a defect. This checklist follows the OWASP API Security Top 10 and shows how to test each item with Postman or Burp Suite and automate it.

Functional tests prove that the API does what it should. Security tests prove that it does only what it should. The OWASP API Security Top 10 (2023) is a good map of where to look.

Only test APIs you're authorized to test: your own product, a staging environment you have permission for, or a bug bounty programme whose scope includes the target. Never run these checks against production data you don't own.

1. Build an inventory of endpoints first

You can't test what you don't know about. Start from the OpenAPI/Swagger file or a Postman collection, then compare it with the traffic your web and mobile apps really send (capture it through Burp Suite or browser dev tools). Look for:

  • Endpoints in traffic but missing from the documentation.
  • Old versions still running, such as /api/v1/ beside /api/v3/.
  • Debug, internal or admin routes that a public client can reach.

This covers API9:2023, Improper Inventory Management. Old versions often lack the checks the new one has, so run every test below against each live version.

2. Test object-level authorization (BOLA)

Broken Object Level Authorization is number one in the list. Log in as two ordinary users, A and B. Request B's object while holding A's token: GET /api/orders/{B's id}, then try PUT and DELETE as well. Expect 403 or 404. Test IDs in the path, query string, JSON body and headers. The full method, including Autorize and regression tests, is in my IDOR testing checklist.

3. Test authentication and tokens

Call each protected endpoint with no token, an expired token, a token for a deleted user and a malformed token. All must return 401. Then check how the token itself is built and checked: signature, algorithm, expiry, audience. The JWT testing checklist covers this in detail. Also try login and password-reset endpoints for unlimited guessing, as described in step 7.

4. Test function-level authorization

Object-level checks ask "is this your record?". Function-level checks ask "are you allowed to call this action at all?". Take a normal user's token and call the routes an admin or manager would use: user management, refunds, exports, configuration. Change the HTTP method too, because a GET may be protected while a DELETE on the same path is not.

curl -i -X DELETE https://staging.example.com/api/admin/users/1042 \
  -H "Authorization: Bearer $NORMAL_USER_TOKEN"
# expected: 403, and the user still exists afterwards

5. Test for mass assignment and excessive data exposure

Two problems share one cause: the API trusts its data model too much.

  • Mass assignment: when creating or updating a record, add fields the client should never control, such as "role": "admin", "isVerified": true, "balance": 99999 or "ownerId". Then read the record back. If the value changed, the API binds request fields straight to the model.
  • Excessive data exposure: read the whole JSON response, not just what the screen shows. Look for password hashes, tokens, internal IDs, other users' emails or phone numbers, and fields the UI quietly hides.

These map to API3:2023, Broken Object Property Level Authorization. A good fix is an allow-list of fields per endpoint, for both input and output.

6. Fuzz inputs and validate types

Send values the developer didn't plan for: strings where numbers are expected, negative or huge numbers, empty arrays, deeply nested JSON, very long strings and special characters. Use boundary values from my boundary value analysis examples to choose them. Expect a clean 400 or 422 with a short message, never a 500 and never a stack trace. Also check that quotes and SQL or script payloads in parameters don't change behaviour (SQL injection, XSS), and that URL-fetching parameters, like an image URL or webhook address, can't be pointed at internal addresses (SSRF).

7. Test rate limits and resource consumption

API4:2023, Unrestricted Resource Consumption, is easy to forget because nothing "breaks" in a normal test. Check these on staging:

  • Login, OTP and password-reset endpoints: after several wrong attempts, do you get 429 or a lockout?
  • List endpoints: does ?limit=1000000 return everything? A sensible maximum page size should be enforced.
  • Expensive operations such as export, search and file upload: is there a size limit, a timeout and a per-user quota?

You can script the burst with k6 and use a few dozen requests, enough to see whether a limit exists without stressing the service.

import http from "k6/http";
import { check } from "k6";

export const options = { vus: 1, iterations: 30 };

export default function () {
  const res = http.post(`${__ENV.BASE_URL}/api/login`,
    JSON.stringify({ email: "qa@example.com", password: "wrong" }),
    { headers: { "Content-Type": "application/json" } });
  check(res, { "throttled at some point": (r) => r.status === 429 });
}

The k6 documentation explains how to run it and read the results.

8. Check configuration, headers and errors

  • HTTPS only: plain HTTP must redirect or be refused, and tokens must never appear in URLs.
  • CORS: Access-Control-Allow-Origin: * together with credentials, or an origin that is simply reflected back, is a defect.
  • Headers: Cache-Control: no-store on sensitive responses, X-Content-Type-Options: nosniff, and no version banners in Server or X-Powered-By.
  • Errors: no stack traces, SQL errors or file paths in responses.
  • Unused methods: send OPTIONS, TRACE and PUT to read-only routes.

9. Automate the checks in Playwright

Every confirmed finding should become a regression test. Playwright's API testing support is enough:

import { test, expect } from "@playwright/test";

test("user A cannot read user B's order", async ({ request }) => {
  const res = await request.get(`/api/orders/${fixtures.userB.orderId}`, {
    headers: { Authorization: `Bearer ${fixtures.userA.token}` },
  });
  expect([403, 404]).toContain(res.status());
});

test("role cannot be set through mass assignment", async ({ request }) => {
  await request.patch("/api/profile", {
    headers: { Authorization: `Bearer ${fixtures.userA.token}` },
    data: { displayName: "QA", role: "admin" },
  });
  const me = await request.get("/api/profile", {
    headers: { Authorization: `Bearer ${fixtures.userA.token}` },
  });
  expect((await me.json()).role).toBe("user");
});

Run them in the same pipeline as your functional tests. The setup is described in QA automation and security testing in one CI pipeline.

10. Report API findings so they get fixed

  • Title: state the effect, for example "A normal user can read any customer's order by changing the ID".
  • Steps: the exact request, the token's role, the response status and the relevant part of the body. A copy-paste curl command helps the developer reproduce it in seconds.
  • Impact: what data or action an attacker could reach, and whether it works on every record or only some.
  • Fix and retest: suggest the server-side check that is missing (ownership check, role check, field allow-list, rate limit), then rerun the automated test once the fix is deployed.

Key takeaways

  • Test what the API should refuse, not only what it should accept.
  • Use two normal users to check object access, and a normal user against admin functions.
  • Add unexpected fields to requests, and read full responses for data the UI hides.
  • Run every test on every live API version and on undocumented endpoints.
  • Check rate limits, page sizes and upload limits, since resource abuse rarely shows up in functional tests.
  • Turn each confirmed finding into an automated test so it stays fixed.

FAQ

What is the difference between API testing and API security testing?

API testing checks that endpoints return the right data for valid requests. API security testing sends invalid, unauthorized and abusive requests to confirm the API refuses them. Both use the same tools, such as Postman or Playwright, but security tests focus on who is calling, what they are allowed to do and how much they can ask for.

Which tools do I need for API security testing?

Postman or Playwright for repeatable requests, Burp Suite or OWASP ZAP to capture and modify traffic, Autorize for automated access-control comparison, and k6 for light rate-limit checks. All of them are free or have a free edition.

Can a QA engineer do API security testing without a security background?

Yes. Most of the OWASP API Top 10 is about authorization, validation and limits, which are things QA already tests. Start with BOLA and function-level checks, learn the OWASP list, and practise on intentionally vulnerable apps such as OWASP Juice Shop or crAPI before testing real systems.
